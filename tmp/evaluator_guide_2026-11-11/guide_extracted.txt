Handwriting Robot Live System Evaluation Guide
Code controls and expected effects for classification and reproduction
11 November 2026
This guide identifies changes an evaluator could reasonably ask to see in the running handwriting robot system. The
aim is to predict the effect of a change, demonstrate the relevant stage, and explain the observation. It covers
classification, segmentation, handwriting synthesis, profile selection, layout and physical execution using existing
trained models. Training changes are outside the live comparison.
The central question is whether changing one assumption produces the effect expected from the algorithm. For
every control, identify where it acts, what should change, what remains comparable, which later stage can override
it, and what observation would contradict the prediction.


How to use this guide
Geometry changes are usually the most predictable: larger spacing separates words and more shear increases slant.
Recognition changes involve trade-offs: a stricter threshold may remove noise and faint strokes together, so
accuracy need not change monotonically. Physical execution changes can affect time, ink deposition and mechanical
tracking while the digital preview remains identical.
The identifiers and defaults below refer to the inspected Software/CleanPipeline3 implementation and its web
server. Some controls are existing request fields, some require changing an argument or constant at its active call
site, and some require a small logic edit. An evaluator request is not evidence that a coefficient has an established
optimum. Expected effects are algorithmic predictions, not new measured results.
For a controlled comparison, keep the source photograph or text, writer, checkpoint, preprocessing, size and seed
fixed except for the selected change. Display the intermediate result nearest that change before interpreting the
final score. A fixed seed improves reproducibility, but a changed branch can consume random values differently and
alter subsequent choices.


Twelve comparisons to prioritise
1. Disable and enable joins while retaining the same writer profile.
2. Compare upright and slanted writing.
3. Compare small and large writing and explain automatic fitting.
4. Compare narrow and wide word spacing.
5. Compare zero jitter with increased jitter.
6. Compare personal variants with stronger anchoring.
7. Compare one candidate with multiple candidates and repair off with repair on.
8. Compare the ink and shape writer models with preparation stated.
9. Compare raw and stroke-normalised writer classification.
10. Change a segmentation threshold or seam setting and show the intermediate crops.
11. Compare slower and faster pen-down feed on the same generated geometry.
12. Disable and enable physical endpoint joining and compare pen lifts and added connectors.
For each comparison, state the expected effect before generating or classifying the result. Record whether the
outcome matches the prediction. Use a temporary profile copy for profile experiments and restore the baseline
afterwards.

Settings that are not useful ordinary live controls
Training learning rate, batch size, dropout probability, epochs and optimiser do not change ordinary inference from
fixed saved weights. A change to a training constant is not a live classification comparison.
CNN channel counts, LSTM hidden size and alphabet order are tied to checkpoint shapes and label semantics. They
are not compatible ordinary tuning parameters. Input height and width alter preparation, but also change the input
distribution and frame geometry; they are poor first choices for an interpretable live adjustment.
The inspected GantryConfig declares accelMmS2, but the inspected motion path does not consume that field. Do
not promise an acceleration demonstration by changing it alone. SQUARENESS_ERROR_DEG is likewise declared
without being applied as a motion correction.
Changing letterAdvance alone may have little effect on normal stored glyphs because they use their own width, lead
and advance through _Advance. The summary table can matter more for fallback cases.
Render pen width changes a raster preview or judging input. It does not change the physical nib width or contact
force. Steps per millimetre, microstepping and measured switch travel encode calibration or hardware
configuration; arbitrary edits can change scale without constituting a valid calibration.

Questions to answer for every requested change
1. Where in the pipeline does this value act, and what are its units?
2. Is it an existing request field, a call argument, a constant, a small logic edit or a profile-regeneration setting?
3. What should increase, decrease or remain unchanged?
4. Which guard, cap, cache or later stage can override the change?
5. What intermediate image, path, crop, label or timing would make the effect visible?
6. Does the comparison keep the model, input, seed and unrelated settings consistent?
7. Does a higher internal score represent independent evidence of a better physical result?
8. What observation would show that the initial prediction was wrong?
9. How is the original baseline restored?
An unchanged final output can be informative: it may reveal a disabled branch, cached value, eligibility gate,
quantised kernel, inactive configuration field or downstream compensation. Explain that mechanism rather than
repeatedly changing coefficients without checking the active path.
